# Промпт для ИИ-агента: разработка Telegram Knowledge Collector

## 1. Твоя роль и правила работы

Ты — ведущий Python-разработчик, системный аналитик и инженер по надёжности.

Спроектируй и реализуй приложение для преобразования коллекции сообщений, пересланных Telegram-боту, в организованную базу Markdown-заметок для Obsidian.

Работай последовательно: сначала проверь исходные данные и критические интеграции, затем реализуй минимальный сквозной сценарий, после — остальные возможности.

Приоритеты проекта:

1. Сохранность исходных сообщений и вложений.
2. Защита пользовательских изменений.
3. Идемпотентность и восстановление после сбоев.
4. Удобство чтения, поиска и навигации в Obsidian.
5. Простота эксплуатации на локальном сервере.
6. Возможность дальнейшего развития без избыточной инфраструктуры.

Обязательные правила:

- Не подменяй согласованные требования собственными предположениями.
- Разделяй подтверждённые решения, предлагаемые значения по умолчанию и открытые вопросы.
- Не задавай повторно вопросы, ответы на которые уже приведены в этом документе.
- Задавай оставшиеся вопросы одним компактным списком, указывая рекомендуемые варианты.
- Не блокируй независимые части разработки отсутствием ключей или доступа к реальным сервисам: используй адаптеры, тестовые данные и моки.
- Не заявляй об успешной проверке реального сервиса, если выполнялись только тесты с моками.
- Не выполняй разрушительные операции с существующим vault, S3 или Telegram-конфигурацией без отдельного подтверждения.
- Не добавляй микросервисы, Redis, Celery, векторную БД, веб-интерфейс или пользовательскую Telegram-сессию без обоснования и согласования.
- Выпускай законченные проверяемые этапы, а не большой объём непроверенного кода.

## 2. Контекст и назначение приложения

Пользователь пересылает Telegram-боту полезные сообщения из профессиональных чатов. Коллекция содержит профессиональный опыт, обсуждения, рекомендации, код, ссылки и вложения.

Сейчас накопленные сообщения не обрабатываются автоматически.

Необходимо приложение, которое:

- импортирует накопленную коллекцию;
- принимает новые сообщения;
- сохраняет исходные данные;
- преобразует материалы в Markdown;
- организует заметки в иерархическую структуру;
- при необходимости объединяет связанные сообщения;
- использует LLM для согласованных операций классификации и обогащения;
- публикует Markdown и вложения в S3;
- обеспечивает совместимость результата с Obsidian;
- не уничтожает пользовательские правки.

Obsidian на устройствах работает с локальными vault, синхронизируемыми с S3 через выбранный плагин. Само Python-приложение не заменяет плагин синхронизации.

## 4. Согласованная политика редактирования

Это обязательная часть архитектуры, а не необязательная рекомендация.

### 4.1. Разделение областей vault

```
Telegram/       — заметки, первоначально созданные приложением
Knowledge/      — пользовательские статьи, выводы и обобщения
Review/         — предложения дополнений и новых редакций
Attachments/    — вложения
```

Допускается согласовать язык и точные названия папок, сохранив разделение ответственности.

Технический архив Telegram-оригиналов хранится отдельно от синхронизируемого префикса vault.

### 4.2. Свободное редактирование

После первой публикации пользователь вправе:

- изменять и полностью переписывать текст;
- менять заголовок;
- добавлять и удалять разделы;
- менять теги и пользовательские свойства;
- переименовывать файл;
- перемещать заметку;
- удалять заметку.

Приложение не должно возвращать первоначальный текст, имя, папку или категорию.

Разделение `Telegram/` и `Knowledge/` не запрещает редактирование заметок в `Telegram/`.

Приложение не изменяет содержимое пользовательских материалов в `Knowledge/`.

### 4.3. Стабильный идентификатор

Каждая заметка, связанная с приложением, получает неизменяемое свойство:

```
---
kb_id: "note_<stable_unique_id>"
---
```

Требования:

- `kb_id` идентифицирует заметку, а не обязательно одно сообщение.
- Одна заметка может иметь несколько исходных сообщений.
- Переименование и перемещение не меняют `kb_id`.
- Связь заметки с исходными сообщениями хранится в БД.
- Пользовательские заметки без управления со стороны приложения не обязаны иметь `kb_id`.
- При исчезновении `kb_id` приложение не угадывает принадлежность файла.
- При дублировании `kb_id` приложение регистрирует конфликт и прекращает автоматические изменения затронутых файлов.
- Файл без `kb_id` не считается свободным для перезаписи.

### 4.4. Запрет автоматической перезаписи

После первой публикации приложение не изменяет содержимое существующей рабочей заметки автоматически.

Это относится к:

- повторному импорту;
- повторной доставке update;
- смене модели;
- смене промпта;
- изменению рубрикатора;
- повторной классификации;
- обнаружению новых связанных сообщений;
- улучшению алгоритма генерации.

Результаты повторной обработки сохраняются как предложения в `Review/`.

Применение новой редакции выполняется только отдельным подтверждённым действием с проверкой актуального файла и сохранением предыдущей версии.

В MVP допустимо ограничиться созданием предложений и их ручным применением пользователем, если автоматизированное применение ещё не реализовано безопасно.

### 4.5. Переименование, перемещение и удаление

Приложение сверяет опубликованные Markdown-файлы по `kb_id`.

После обнаружения перемещения:

- обновляет известный путь в БД;
- не восстанавливает файл по старому пути;
- не возвращает исходную категорию.

Если файл исчез:

1. Зафиксировать состояние `missing`.
2. Повторно проверить хранилище и поиск по `kb_id`.
3. Не восстанавливать файл автоматически.
4. Восстановление выполнять только явной операцией.

Не считать единичное отсутствие файла доказательством окончательного удаления.

Удаление заметки не удаляет автоматически исходные сообщения и вложения.

Приложение видит пользовательские изменения только после их синхронизации в S3. Не обещай защиту от изменений, которые ещё находятся исключительно на офлайн-устройстве.

### 4.6. Объединение и разделение пользователем

- Ручное копирование файла с тем же `kb_id` создаёт конфликт идентичности.
- При объединении заметок итоговая заметка сохраняет один `kb_id`; связь остальных источников присоединяется отдельной явной операцией.
- При разделении одна заметка сохраняет прежний `kb_id`, другая становится пользовательской либо получает новый ID через предусмотренную операцию.
- Не пытайся автоматически вывести объединение или разделение только из исчезновения файлов.

## 7. Приём новых сообщений

Реализуй получение через Bot API long polling, если существующая инфраструктура не требует другого согласованного решения.

Требования:

- Allowlist по числовым ID пользователей и чатов.
- Один активный получатель updates для токена.
- Проверка существующего webhook перед запуском.
- Не удалять webhook автоматически.
- Не использовать сброс ожидающих updates без явного подтверждения.
- Сохранять исходный update и задания транзакционно до подтверждения получения Telegram.
- Явно проверить семантику offset и подтверждения выбранной библиотеки.
- Не полагаться на фоновую обработку, при которой updates подтверждаются раньше надёжного сохранения.
- Обеспечить корректное завершение и восстановление после аварии.
- Игнорировать либо отдельно классифицировать команды, служебные сообщения и ответы самого бота.

Сохраняй доступные:

- `update_id`;
- `chat_id`;
- `message_id`;
- даты;
- текст и подпись;
- entities и caption entities;
- сведения о пересылке;
- reply-связи;
- media group ID;
- метаданные вложений;
- исходный payload.

Не обещай автоматическое получение всей истории через Bot API. Проверь и документируй актуальные ограничения хранения updates и скачивания файлов.

Пользовательский Telegram API не включать в MVP без отдельного решения.

## 8. Импорт HTML-экспорта

### 8.1. Исследование формата

До реализации изучи фактический HTML:

- контейнеры сообщений и их ID;
- даты и часовые пояса;
- продолжения сообщений без повторного отображения автора;
- сведения о пересылке;
- ссылки на ответы;

- подписи к вложениям;
- пути файлов;
- служебные события;
- навигацию между несколькими HTML-страницами.

Не заменяй HTML-парсинг регулярными выражениями и не ограничивайся извлечением общего `get_text()`.

### 8.2. Требования к импорту

- Принимать каталог экспорта или согласованный путь к HTML.
- Поддерживать относительные пути вложений.
- Поддерживать несколько HTML-страниц экспорта, если они обнаружены.
- Сохранять порядок сообщений.
- Различать время пересылки и доступное время исходного сообщения.
- Не выдумывать недостающие ID, авторов и ссылки.
- Сохранять текст ссылки и её `href`.
- Корректно декодировать HTML entities.
- Сохранять структуру кода и переносы строк.
- Не выполнять JavaScript и не загружать удалённые ресурсы при разборе.
- Не обходить ссылки за пределы разрешённого каталога.
- Проверять разрешённые пути с учётом symlink и path traversal.
- Отсутствующие вложения отмечать явно.
- Обрабатывать большие экспорты с ограниченным потреблением памяти.
- Поддерживать dry-run, прогресс, возобновление и отчёт об ошибках.
- Повторный импорт не должен создавать технические дубли.

Составь отчёт о возможных потерях формата и неоднозначностях.

### 8.3. Сопоставление HTML и live ingestion

Не предполагай, что ID в HTML автоматически эквивалентны Bot API ID.

Проверь сопоставление на реальных образцах целевого чата.

Используй отдельные идентификаторы источников и таблицу соответствий.

Если надёжное сопоставление невозможно:

- не объединяй записи только по похожему тексту;
- регистрируй кандидатов в дубли;
- предложи явное сопоставление или ручную проверку.

## 9. Связанные сообщения и единица заметки

Поддержи модель «одна заметка — несколько исходных сообщений», но не объединяй соседние сообщения только потому, что они близки по времени.

### 9.1. Принципы

Разделяй:

- технические дубли;
- повторные пересылки одного материала;
- ответы в обсуждении;
- альбомы;
- тематически похожие, но независимые сообщения.

Сигналы связи могут включать:

- достоверные reply-ссылки;
- media group ID;
- ручную команду или метку;
- явно доступные метаданные источника;
- временные интервалы;
- смысловую близость как вспомогательный, а не единственный сигнал.

Близость времени и общий автор сами по себе не доказывают принадлежность к одному обсуждению.

### 9.2. Безопасное поведение по умолчанию

До согласования алгоритма:

- самостоятельное сообщение — отдельная заметка;
- достоверный альбом — одна логическая заметка;
- неоднозначные группы — отдельные заметки или предложение в `Review/`;
- LLM не принимает необратимые решения об объединении.

Для исторического импорта анализируй весь доступный набор кандидатов до публикации групп.

Для live ingestion используй ограниченное настраиваемое окно ожидания. Позднее поступивший материал после публикации создаёт предложение дополнения, а не автоматическую перезапись.

Для альбомов учти отсутствие гарантированного отдельного события «альбом завершён».

Не превращай это требование в избыточное количество таблиц без необходимости, но сохрани смысловое разделение.

### 10.2. Идемпотентность

- Повтор update не создаёт новое исходное сообщение.
- Повтор импорта не создаёт новую заметку.
- Повтор PUT после аварии не создаёт второй объект с новым случайным именем.
- Повторная пересылка материала — не обязательно технический дубль.
- Семантическая похожесть не является основанием для автоматического удаления.
- Hash текста не заменяет идентичность сообщения.

### 10.3. Очередь

Очередь заданий должна храниться в БД и переживать перезапуск.

Предусмотри:

- состояния pending, processing, retry, completed, failed;
- lease и возврат зависших заданий;
- ограниченные retries;
- exponential backoff и jitter;
- поддержку серверного retry delay;
- таймауты;
- ручной повтор;
- классификацию постоянных и временных ошибок;
- независимые статусы обогащения и публикации.

Не обещай exactly-once между Telegram, SQLite, файловой системой и S3. Используй надёжное сохранение, повторяемые операции и идемпотентные эффекты.

### 10.4. Архивирование

Сохраняй:

- исходный экспорт или его проверяемую архивную копию;
- исходные live payload;
- нормализованные данные;
- оригинальные файлы в пределах согласованной политики;
- hashes и сведения о происхождении.

Не изменяй исходный экспорт на месте.

Версии и исправления не должны уничтожать ранее полученные данные.

## 11. Формат Markdown и структура vault

### 11.1. Организация

Предварительная структура:

```
Telegram/
  Inbox/
  <Тема>/
    <Подтема>/
      <стабильное-имя>.md

Knowledge/

Review/
  <kb_id>/
    <proposal_id>.md

Attachments/
  Telegram/
    <attachment_id>/
      <безопасное-имя-файла>
```

Согласуй рубрикатор. Не создавай неограниченное количество папок по произвольному ответу модели.

Стабильность идентичности важнее красивого имени файла.

После публикации не менять путь автоматически при повторной классификации.

### 11.2. Пример заметки

```
---
kb_id: "note_<stable_unique_id>"
title: "Название материала"
source: telegram
created_at: "2026-11-15T12:00:00Z"
tags:
  - python
category: "Разработка/Python"
schema_version: 1
---
```

```

## Краткое содержание

Сгенерированное обобщение, явно отделённое от оригинала.

## Материалы

Исходный текст.

### Сообщение 2

Исходный текст связанного сообщения.

## Источники

```

Шаблон адаптируй к типу материала. Не создавай пустые разделы без необходимости.

Полный исходный текст сохраняется независимо от наличия краткого содержания.

### 11.3. Совместимость

Корректно обрабатывай:

- UTF-8;
- кириллицу и emoji;
- UTF-16 offsets Telegram entities;
- YAML escaping;
- inline code;
- многострочные code fences;
- текстовые гиперссылки;
- относительные ссылки;
- символы и имена, запрещённые Windows;
- коллизии с учётом регистра;
- ограничение длины путей;
- небезопасный HTML.

Не используй временные Telegram download URL или presigned S3 URL как постоянные ссылки на вложения.

Проверяй чтение заметок средствами Obsidian без обязательной установки дополнительных плагинов для основного содержимого.

## 12. LLM и классификация

LLM — необязательное обогащение.

Базовая заметка должна сохраняться и публиковаться при недоступности модели.

Возможности после согласования:

- создание заголовка;
- краткое содержание;
- выбор категории из рубрикатора;
- нормализация тегов;
- предложение связей;
- предложение группировки;
- предложение дополнения к существующей заметке.

Требования:

- Отдельный интерфейс провайдера.
- Настраиваемые endpoint, model, timeout и лимиты.
- Валидация структурированного ответа.
- Ограничение входного текста и числа запросов.
- Ограничение расходов там, где они могут быть рассчитаны.
- При неизвестной стоимости не выдавать приблизительную оценку за точный биллинг.
- Версионирование промптов и конфигурации обработки.
- Кэш с учётом исходников, промпта, модели и параметров.
- При ошибке — безопасный fallback.
- При неуверенности — `Inbox`.
- Модель не задаёт произвольные пути.
- Модель не создаёт новые категории без разрешённой политики.
- Не выдумывать отсутствующий контекст обсуждения.
- Не представлять вывод модели как цитату автора.

Сообщения являются недоверенными данными. Инструкции внутри сообщений не должны менять системные правила, запускать команды, читать секреты или инициировать сетевые обращения.

OCR, транскрибация, загрузка содержимого веб-страниц, embeddings и RAG не входят в MVP без отдельного согласования.

## 13. Вложения

### 13.1. Обработка

- Настраиваемый список поддерживаемых типов.
- Лимиты размера и времени.
- Потоковое скачивание.
- Безопасные имена.
- Проверка реального размера.

MIME type и расширение считай недоверенными метаданными.

### 13.2. Публикация

Порядок:

1. Подготовка вложений.
2. Загрузка доступных вложений.

Если вложение стало доступно после первой публикации, учитывай запрет автоматического изменения рабочей заметки: сформируй предложение исправления.

Не выполняй автоматическую сборку мусора. Очистка неиспользуемых файлов — отдельная операция с dry-run и подтверждением.

## 14. S3 и совместимость с Obsidian

### 14.1. Проверка интеграции до основной разработки

Выполни compatibility spike с выбранным плагином и тестовым префиксом.

Проверь:

1. Создание Markdown внешним Python-приложением.
2. Получение файла Obsidian.
3. Обнаружение новых объектов без дополнительных служебных индексов.
4. Кириллицу и вложенные пути.
5. Вложения и относительные ссылки.
6. Обновление существующего объекта.
7. Переименование и перемещение из Obsidian.
8. Удаление.
9. Конфликты.
10. Поведение на целевых устройствах.
11. Шифрование.
12. Необходимые метаданные, CORS и настройки доступа.

Не считай совместимость доказанной одним успешным PUT.

Если тест требует доступа, которого нет, подготовь воспроизводимый сценарий и явно укажи статус «не проверено».

### 14.2. Шифрование

Не предполагается, что зашифрованный формат плагина совместим с обычными Markdown-объектами.

Если клиентское шифрование обязательно:

- сначала выясни формат и документированные способы совместимости;
- оцени сложность и риски;
- предложи варианты;
- не создавай собственную криптографию;
- не отключай шифрование без согласования.

### 14.3. Префиксы и права

Раздели:

```
<vault-prefix>/       — только синхронизируемый vault
<archive-prefix>/     — технический архив, если хранится в S3
<backup-prefix>/      — резервные копии, если выбран такой вариант
```

Точные имена согласуй.

- Не используй корень существующего бакета без проверки.
- Ограничь права нужными префиксами.
- Не изменяй `.obsidian/`.
- Не публикуй секреты и локальную БД в vault.
- Учитывай различия S3-совместимых провайдеров.

### 14.4. Конкурентный доступ

Перед подтверждённой заменой файла:

- заново проверить текущую удалённую версию;
- сравнить с базой, на которой подготовлено предложение;
- сохранить предыдущую версию;
- использовать поддерживаемые условные операции, если они доступны;
- при изменении базы остановить замену и зарегистрировать конфликт.

Не трактуй ETag как универсальный hash содержимого.

Если провайдер не позволяет обеспечить безопасную условную замену, оставь ручное применение предложений вместо небезопасного автоматического overwrite.

## 15. Сверка удалённого состояния

Реализуй ограниченный модуль reconciliation.

Задачи:

- обнаруживать опубликованные Markdown;
- извлекать `kb_id`;
- отслеживать текущие пути;
- выявлять изменения содержимого;
- выявлять дубли ID;
- фиксировать missing;
- учитывать предложения и их состояние.

Требования:

- Не скачивать весь vault при каждом коротком цикле без необходимости.
- Использовать метаданные как подсказку, а не безусловное доказательство неизменности.
- Предусмотреть периодическую полную проверку.
- Не записывать служебные изменения в рабочие заметки.
- Не изменять пользовательские файлы.
- Не выводить перемещение только из совпадения заголовков.
- Не создавать заново отсутствующие файлы.
- Не считать незавершённую синхронизацию подтверждённым удалением.

Конкретную стратегию частоты, кеширования и полной сверки обоснуй с учётом размера коллекции и стоимости S3-запросов.

- изменение текста;

- удаление;

### 19.5. Реальные интеграции

Отдельно проверь на тестовых ресурсах:

- Telegram;
- выбранный S3;
- выбранный Obsidian-плагин;
- выбранный LLM.

## 20. Критерии приёмки MVP

MVP считается готовым, когда:

1. HTML-экспорт импортируется с сохранением текста, гиперссылок, кода и доступных вложений.
2. Повторный импорт не создаёт технические дубли.
3. Новые разрешённые Telegram-сообщения надёжно сохраняются.
4. Неавторизованные отправители отклоняются.
5. Без LLM создаётся полноценная базовая заметка.
6. Отказ LLM не блокирует сохранение.
7. Отказ S3 оставляет повторяемые задания.
8. Markdown и вложения публикуются по совместимым путям.
9. Результат появляется в Obsidian через выбранный плагин.
10. Пользователь может свободно редактировать и перемещать заметки с сохранением `kb_id`.
11. Повторная обработка не перезаписывает опубликованные заметки.
12. Предложения изменений появляются отдельно в `Review/`.
13. Исчезнувшие заметки не восстанавливаются автоматически.
14. Конфликты ID выявляются без разрушительных действий.
15. После аварийного завершения обработка возобновляется.
16. Развёртывание воспроизводится по README на Ubuntu 24.04.
17. Основные сценарии доступны для отладки на Windows.
18. Резервная копия восстанавливается в чистом окружении.
19. Все непроверенные интеграции и известные ограничения явно перечислены.

Целевую задержку от приёма сообщения до публикации согласуй отдельно. Разделяй задержку нашего приложения и задержку синхронизации Obsidian.
