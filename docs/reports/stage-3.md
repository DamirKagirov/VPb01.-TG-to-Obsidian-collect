# Отчёт по этапу 3 — вертикальный срез без LLM

Дата: 2026-11-16. Основание: `prompt.md` §21 (Этап 3), §11, §13.2, §14.4.

## Что реализовано

| Область | Модуль | Содержание |
|---|---|---|
| Идентификаторы | `domain/ids.py` | `kb_id` детерминирован от `(source, chat, message)`, `attachment_id` — от пути в сообщении |
| Имена и пути | `domain/paths.py` | slug с кириллицей, Windows-ограничения, лимит длины, резервные имена |
| Парсер | `ingestion/html_export/` | обнаружение страниц, безопасное разрешение путей, рендеринг текста, forward/reply/joined, медиа и заглушки |
| Markdown | `markdown/` | YAML front matter с `kb_id` в кавычках, шаблон заметки, токены вложений, очистка текста |
| БД | `db/` | SQLAlchemy 2.0, 9 таблиц, Alembic-миграция `e3b630bc2662` |
| Архив | `archive/raw_store.py` | копия страниц экспорта с проверкой sha256 и манифестом |
| Публикация | `publication/` | раскладка vault, `If-None-Match: *`, вложения до заметки |
| Сценарий | `services/import_html.py` | импорт: разбор → архив → БД → S3, dry-run, лимит, идемпотентность |
| CLI | `kbcollector import-html` | `--path`, `--limit`, `--dry-run`, `--target-prefix` |

## Схема БД (миграция применена)

`alembic_version`, `sources`, `raw_messages`, `message_versions`, `attachments`, `notes`,
`publications`, `jobs`, `meta`.

Ключевые ограничения: `UNIQUE(source_kind, chat_id, message_id)`,
`UNIQUE(chat_id, message_id)` для заметок, `UNIQUE(raw_message_id, position)` для вложений.

## Что опубликовано в реальном vault

`vault4-kb01/Telegram/Inbox/` — **839 заметок**, `vault4-kb01/Attachments/Telegram/` —
**117 вложений**. Пользователь подтвердил: 9 первых заметок появились в Obsidian,
кириллица корректна, синхронизация с устройством прошла.

## Дефект, найденный и исправленный в ходе импорта

Пути вложений с пробелами и скобками (`sticker (2).webp`, `AnimatedSticker (1).tgs`)
ломали Markdown-ссылки: `](path (2).webp)` обрывается на первой `)`. Исправлено
обрамлением в `<>`: `[name](<../../Attachments/.../sticker (2).webp>)`.
11 затронутых заметок пересобраны точечно, только после сверки содержимого в S3
с хешем из БД (правки пользователя не затрагивались). Повторная проверка — 117/117 ссылок.

## Что не проверено

* **Все 839 заметок в Obsidian** — пользователь подтвердил только первые 9; полный набор
  ещё не просмотрен на устройстве.
* **Сопоставление HTML ↔ live** — проверено и дало отрицательный результат: ID в HTML
  (`166651`) и `message_id` Bot API (`1138`) для одного и того же сообщения различаются.
  Автоматическое сопоставление по числу невозможно, нужен `id_map` по содержанию
  с ручным подтверждением (Этап 4). См. ADR 0003.
* **Сетевой сбой при первом полном прогоне** — соединение с S3 оборвалось после 455 заметок;
  импорт доработан: сбой отдельного сообщения больше не прерывает пакет, счётчик сбоев
  выводится в отчёте, повторный запуск продолжает с места остановки.

## Известные ограничения этапа

* Одна заметка = одно сообщение; группировка альбомов/ответов — Этап 5.
* Заголовок — эвристика по первой строке; LLM-заголовки — Этап 5.
* `id_map`, `jobs` в работе ещё не используются (таблицы созданы заранее).
* При потере БД повторный импорт того же сообщения даст тот же `kb_id`, но имя файла может
  отличаться при изменении эвристики заголовка — сверка по `kb_id` появится на Этапе 6.
* Заметки, опубликованные до появления вложений, не обновляются автоматически
  (ТЗ §4.4) — для них потребуются предложения в `Review/` (Этап 5–6).

## Как запускать

```powershell
uv run alembic upgrade head
uv run kbcollector import-html --dry-run
uv run kbcollector import-html --limit 10
uv run kbcollector import-html            # весь экспорт
```
