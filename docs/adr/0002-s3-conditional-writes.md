# ADR 0002: Условные записи S3 и сохранение предыдущей версии

* **Статус:** принято (на основании измерений)
* **Дата:** 2026-11-16
* **Основание:** ТЗ §4.4, §14.4; спайк `spikes/s3_compat.py`

## Контекст

Перед заменой опубликованной заметки нужно убедиться, что удалённый объект не изменился
с момента подготовки предложения. Провайдер — Selectel Object Storage.

## Измерено

| Операция | Результат |
|---|---|
| `PUT` + `If-None-Match: *` по существующему ключу | `412 PreconditionFailed` |
| `PUT` + `If-Match: <актуальный ETag>` | успех |
| `PUT` + `If-Match: <устаревший ETag>` | `412 PreconditionFailed` |
| Версионирование bucket | `NotEnabled` |
| ETag одночастной загрузки | MD5 содержимого |

## Решение

1. **Создание** объекта — `If-None-Match: *`. Это делает повторную публикацию идемпотентной
   и исключает гонку с плагином синхронизации.
2. **Замена** — `If-Match` с ETag, прочитанным при подготовке предложения. При `412`
   замена не выполняется, создаётся запись конфликта `stale_base`.
3. **Предыдущая версия** всегда копируется в `<backup-prefix>/notes/<kb_id>/<utc-timestamp>.md`
   до замены: версионирования в bucket нет, откат иначе невозможен.
4. **ETag не считается хешем**: для multipart-загрузок он иной. Сверка использует
   `ETag + size` как подсказку и sha256 при сомнении.
5. В MVP применение предложений — **ручная команда** (`proposals apply --id …`), безопасная
   благодаря пунктам 1–3. Автоматическое применение возможно позже, отдельным решением.

## Последствия

* Невозможна ситуация «перезаписали правку пользователя»: либо `If-Match` совпал,
  либо получили `412` и остановились.
* Требуется хранение `base_etag`/`base_sha256` в записи предложения.
* Дополнительное место в `backup/` — принимается (ТЗ §14.3).

## Проверка

Подтверждено спайком 2026-11-16 (см. `docs/s3-obsidian.md`). Провайдерская поддержка
условных записей может отличаться у другого S3-провайдера — при смене провайдера спайк
запускается повторно.
