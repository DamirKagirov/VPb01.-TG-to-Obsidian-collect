# ADR 0001: Модульный монолит, SQLite и очередь заданий в БД

* **Статус:** принято
* **Дата:** 2026-11-16
* **Основание:** ТЗ §5, §10

## Контекст

Нужен конвейер: приём сообщений → архив → нормализация → заметки → публикация в S3 →
сверка. Объём — личная коллекция (тысячи сообщений), один оператор, локальная ВМ Ubuntu 24.04.
ТЗ прямо запрещает микросервисы, Redis, Celery и внешнюю БД без обоснования.

## Решение

1. Один Python-процесс: CLI-команды + воркер очереди в том же процессе (`kbcollector run`).
2. Состояние — SQLite на persistent volume, режим WAL, `busy_timeout`, `foreign_keys=ON`,
   один писатель (воркер), чтение параллельно.
3. Схема — SQLAlchemy 2.0 + Alembic (миграции обязательны по ТЗ §5).
4. Очередь — таблица `jobs` с `dedupe_key`, `lease_until`, `attempts`, `next_run_at`;
   захват через `BEGIN IMMEDIATE` + `UPDATE … RETURNING` (SQLite ≥ 3.35, подтверждено `doctor`).
5. Слои: `domain` (без I/O) → `db/repositories` → `jobs/handlers` (единственное место,
   где есть внешние вызовы) → `publication`/`s3`.

## Последствия

* Нет distribution-налога: отладка на Windows и запуск в Docker идентичны.
* Горизонтальное масштабирование не поддерживается и не планируется; при росте объёма
  единственный кандидат на вынос — LLM-обогащение, и только по замеру.
* Exactly-once между Telegram, SQLite и S3 не обещается: только идемпотентные эффекты
  и повторяемые операции (ТЗ §10.3).

## Проверка

* `doctor`: SQLite 3.50.4, `journal_mode=WAL` — OK.
* Этап 3: тест «остановка после PUT, до фиксации в БД» → повтор не создаёт дубль.
