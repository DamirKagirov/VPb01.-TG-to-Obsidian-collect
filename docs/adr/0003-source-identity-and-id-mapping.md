# ADR 0003: Идентичность сообщений и сопоставление HTML ↔ live

* **Статус:** принято частично (сопоставление требует проверки)
* **Дата:** 2026-11-16
* **Основание:** ТЗ §4.3, §8.3, §10.2

## Контекст

Нужны стабильные идентификаторы для сообщений, заметок и связей, при этом HTML-экспорт
и Bot API — разные источники, и их ID нельзя считать эквивалентными без проверки.

## Что установлено

* В HTML `id="message<id>"` — внутренне консистентный идентификатор: 200 из 200 reply-ссылок
  разрешаются в существующие узлы `message<id>`.
* `chat_id` в HTML **отсутствует**.
* Живой приём даёт `chat_id` + `message_id`; HTML — только `<id>` +
  сконфигурированный `chat_id`.
* **Проверено на реальном сообщении (2026-11-16):** сообщение «тест 2026-11-16 1313»
  пришло через Bot API с `message_id = 1138` и датой `2026-11-16 13:14:08 +03:00`,
  а в HTML-экспорте то же сообщение имеет `id="message166651"` с той же датой.

### Вывод из проверки

ID в HTML-экспорте и `message_id` Bot API — **разные пространства идентификаторов**,
даже для одного и того же чата и одного и того же сообщения. Это ровно тот случай,
о котором предупреждает ТЗ §8.3.

Следствия:

* автоматическое сопоставление HTML ↔ live **по числу невозможно**;
* `message_id` нельзя использовать как общий ключ между источниками;
* сопоставление возможно только по содержанию (хеш текста + дата ± допуск) и только
  как кандидат с ручным подтверждением.

## Решение

1. Идентичность сообщения — `(source_kind, chat_id, message_id)` с уникальным индексом;
   `source_kind ∈ {html_export, telegram_live}`. Telegram `update_id` хранится отдельно
   и не используется как идентификатор сообщения.
2. `chat_id` для HTML-импорта задаётся конфигурацией `KBC_HTML_CHAT_ID`; при отсутствии
   импорт не начинается (нельзя угадывать принадлежность чата).
3. Для заметок — `kb_id = "note_" + uuid5(...)` от `(source_kind, chat_id, message_id)`:
   стабилен при повторном импорте и при потере БД.
4. Сопоставление источников — таблица `id_map` (`status ∈ candidate|explicit|manual`).
   Кандидаты формируются по содержанию и дате; автоматическое объединение запрещено.
   Похожесть текста сама по себе не является основанием (ТЗ §8.3, §10.2).
5. Hash текста — атрибут версии (`message_versions`), а не идентификатор сообщения.

## Что осталось проверить (S4, уточнение)

Открытый вопрос: считается ли HTML-ID «номером сообщения в чате» для других клиентов
(например, при переходе по `t.me/c/.../<id>`) — если да, сопоставление можно сделать
через пользовательскую ссылку. До проверки связь остаётся `candidate` с ручным
подтверждением.

## Последствия

* Один и тот же материал, полученный и из экспорта, и через бота, не создаст две заметки
  автоматически — появится кандидат на сопоставление.
* Переименование/перемещение заметки не влияет на `kb_id` и на связи с источниками.
