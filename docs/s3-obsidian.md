# S3 ↔ Obsidian: отчёт о совместимости (спайк S1/S2)

Дата: 2026-11-16. Стенд: Selectel Object Storage, `endpoint=https://s3.ru-7.storage.selcloud.ru`,
`region=ru-7`, `bucket=obsidian-kb01`, vault-префикс `vault4-kb01/`.

Воспроизведение: `uv run python spikes/s3_compat.py --json docs/reports/s3-spike.json`
(работает в изолированном префиксе `_spike/<uuid>/` и удаляет за собой объекты).

## 2. Что это меняет в архитектуре

1. **Условные записи поддерживаются полноценно** (`If-Match` и `If-None-Match`).
   Значит, безопасная замена опубликованной заметки технически возможна → ADR 0002.
   При этом MVP по ТЗ §4.4 всё равно применяет изменения только по явной команде.
2. **ETag = MD5** только для одночастных объектов. Для multipart-загрузок ETag не будет
   MD5, поэтому сверка обязана считать sha256 при сомнении, а ETag использовать как подсказку.
3. **Версионирование выключено.** Удалённая или перезаписанная версия не восстанавливается
   средствами провайдера → перед любой заменой приложение само копирует предыдущую версию
   в `<backup-prefix>/`. Без этого «сохранение предыдущей версии» из ТЗ §14.4 невыполнимо.
4. **Переименование = copy+delete.** При сверке это выглядит как «новый ключ + исчезновение
   старого»; связывать их можно только по `kb_id` в содержимом, не по ETag и не по имени.

## 3. Сторона Obsidian (Remotely Save 0.5.25)

**Статус: не проверено.** На устройствах пользователя спайк не выполнялся; ниже — что
именно нужно подтвердить. Плагин поддерживает префикс в bucket, что и позволяет держать
vault в `vault4-kb01/` рядом с `archive/` и `backup/`.

Настройки, которые должны совпадать с приложением:

| Параметр Remotely Save | Значение |
|---|---|
| Remote service | S3 (or compatible) |
| Endpoint | `https://s3.ru-7.storage.selcloud.ru` |
| Region | `ru-7` |
| Bucket | `obsidian-kb01` |
| Prefix | `vault4-kb01` (без ведущего/завершающего слэша — как в плагине) |
| Encryption | **выключено** (приложение публикует обычные Markdown-объекты) |
| Access key | отдельный ключ с правами только на `vault4-kb01/`, `archive/`, `backup/` |

### Чек-лист проверки на устройстве

1. Файл, созданный приложением в `vault4-kb01/Telegram/Inbox/`, появляется в Obsidian.
2. Кириллица в имени файла и в тексте отображается корректно.
3. Вложенный путь (`Telegram/Inbox/…`) сохраняется, папки создаются.
4. Вложение по относительной ссылке открывается из заметки.
5. Изменение существующего объекта подхватывается без ручного вмешательства.
6. Переименование и перемещение заметки внутри Obsidian не ломают `kb_id`.
7. Удаление заметки в Obsidian отражается в bucket (и наоборот — не воскрешается приложением).
8. Одновременное изменение с двух устройств даёт предсказуемый конфликт, а не потерю данных.
9. Поведение плагина при `412`/ошибке сети (повтор, откат, сообщение пользователю).
10. Задержка появления объекта на втором устройстве (для оценки SLA синхронизации).

Пункты 1–4 проверяются одним PUT из `spikes/s3_compat.py --keep`: скрипт оставит объект
в `_spike/…`, но для проверки в Obsidian нужен объект внутри `vault4-kb01/`. До Этапа 3
это делается вручную через консоль провайдера либо временной командой публикации.

## 4. Ограничения и риски

| Риск | Оценка |
|---|---|
| Плагин кэширует список файлов и не замечает внешние изменения сразу | Проверить п. 5 чек-листа; при необходимости — интервал синхронизации |
| Плагин может писать служебные файлы в vault-префикс | Не трогаем `.obsidian/` и чужие объекты; сверка игнорирует всё вне `Telegram/`, `Knowledge/`, `Review/`, `Attachments/` |
| Удаление в Obsidian и «missing» в приложении | Приложение не восстанавливает файлы автоматически (ТЗ §4.5) |
| Шифрование плагина | Выключено; включение сделает plain Markdown нечитаемым — отдельное решение |
| Multipart-загрузка больших вложений | ETag ≠ MD5; сверка по размеру + sha256 |

## 5. Итог

S3-сторона готова к Этапу 3: запись, чтение, кириллица, вложенные пути, условные записи,
переименование и удаление работают. Сторона Obsidian остаётся **непроверенной** до
подтверждения чек-листа на устройстве — это фиксируется в отчётах как известное ограничение,
а не как успешная интеграция (ТЗ §14.1).
