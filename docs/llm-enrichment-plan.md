# План LLM-обогащения

Дата: 2026-11-16. Основание: ТЗ §12, §4.4, §9.2, ADR 0006/0007.
Провайдер: OpenAI-совместимый endpoint (`https://api.deepseek.com`, модель `deepseek-flash`).
Потрачено токенов на текущий момент: **0** (LLM в конвейере ещё не вызывался).

## 1. Цель и границы

Обогащение — **необязательный** шаг. Базовая заметка (текст, вложения, `kb_id`, дата)
публикуется всегда, даже если модель недоступна.

Что делает модель:

| Поле | Ограничение |
|---|---|
| `title` | заголовок до 80 символов, без Markdown-разметки |
| `summary` | 2–4 предложения, не цитата автора, только по тексту |
| `category` | **только** из рубрикатора, иначе `Inbox` |
| `tags` | 3–6 нормализованных тегов, нижний регистр, без `#` |
| `related` | предложение связей с другими материалами (необязательно, этап 2) |

Чего не делаем в этом объёме: OCR, транскрибация, загрузка веб-страниц, embeddings/RAG,
автоматическое переписывание опубликованных заметок.

## 2. Принципы

1. **Новые материалы** обогащаются до первой публикации — это разрешено: заметки ещё нет.
2. **Опубликованные 839 заметок** не переписываются: результат идёт предложением в `Review/`.
3. Модель не задаёт пути и не создаёт категории — только выбирает из списка.
4. Текст сообщений — недоверенные данные: инструкции внутри не могут менять системные
   правила, вызывать инструменты или раскрывать секреты.
5. Ошибка модели не блокирует публикацию: fallback — базовая заметка и `Inbox`.
6. Ответ валидируется схемой; невалидный JSON отбрасывается, а не «чинится» догадками.
7. Кэш по `input_hash`: повторный прогон с теми же промптом/моделью/входом бесплатен.

## 3. Архитектура

```
classification/  — рубрикатор (готов)
llm/
  base.py            # Protocol: complete_structured(messages, schema) -> LLMResult
  openai_compat.py   # HTTP-адаптер (httpx), timeout, retries, usage
  prompts.py         # загрузка версионируемых промптов, рендер
  schema.py          # pydantic-модель Enrichment + нормализация
  guard.py           # лимиты входа, бюджет, запрет инструментов
  cache.py           # generations: поиск/запись по input_hash
  service.py         # enrich_message(): кэш → вызов → валидация → fallback
config/prompts/
  enrich.v1.md       # системный промпт + шаблон входа
  enrich.v1.schema.json
```

Промпт и схема версионируются вместе с кодом. Смена версии меняет `input_hash`
и инвалидирует кэш — это осознанное решение, а не побочный эффект.

## 4. Контракт ответа

```json
{
  "title": "Заголовок материала",
  "summary": "2–4 предложения по существу.",
  "category": "Inbox",
  "tags": ["python", "asyncio"],
  "confidence": 0.0,
  "language": "ru"
}
```

Правила валидации:

* `category` обязана входить в `rubricator.categories`, иначе `Inbox`;
* `tags`: 0–6, нижний регистр, без `#`, без пробелов по краям, дедупликация;
* `title`: обрезка до 80 символов, удаление `#`, `[]()`, переводов строк;
* `summary`: обрезка до 600 символов; пустое значение допустимо;
* `confidence < 0.5` → `category = Inbox` (модель не уверена);
* неизвестные поля игнорируются, отсутствующие — ошибка схемы.

## 5. Данные и кэш

Новая таблица `generations` (миграция Alembic):

| Поле | Назначение |
|---|---|
| `id` | uuid7 |
| `source_kind`, `chat_id`, `message_id` | к чему относится |
| `prompt_version`, `model`, `params_json` | воспроизводимость |
| `input_hash` (unique) | ключ кэша |
| `input_tokens`, `output_tokens`, `cost_usd` (nullable) | учёт расходов |
| `output_json`, `status` | результат или ошибка |
| `created_at` | время |

`cost_usd` заполняется только если цена известна; иначе `NULL` — приблизительная оценка
не выдаётся за точный биллинг.

## 6. Потоки

### 6.1. Новые материалы (импорт/live)

```
parse → rubricator(rule) → LLM enrich → validate → render note → publish
                              ↓ ошибка
                        baseline (Inbox, title из текста)
```

Меняется только `import_html`: категория берётся из результата модели (если валидна),
заголовок — из `title`, добавляется раздел «Краткое содержание» (явно отделён от оригинала).

### 6.2. Существующие 839 заметок

```
message → LLM → proposal (Review/<kb_id>/enrich-<hash>.md)
```

Предложение содержит: текущий заголовок, предлагаемый заголовок/резюме/категорию/теги,
`base_sha256` опубликованной заметки и пометку «не применено». Заметка не меняется.

### 6.3. Применение предложений (следующий этап)

Только по явной команде: сверка `base_sha256`/`If-Match`, сохранение предыдущей версии
в `backup/`, замена. При расхождении — конфликт и остановка (ADR 0002).

## 7. CLI

```text
kbcollector enrich [--path DIR] [--limit N] [--since YYYY-MM-DD]
                   [--dry-run] [--propose] [--budget-tokens N]
                   [--model NAME] [--no-cache]
kbcollector proposals list|show|apply     # этап 5–6
```

* `--dry-run` — показать первые N результатов, ничего не писать;
* `--propose` — опубликовать предложения в `Review/` (для существующих заметок);
* `--budget-tokens` — жёсткий предел расхода за запуск (вход+выход), после него остановка;
* отчёт: запросов, кэш-хитов, вход/выход токенов, ошибок по типам, средняя латентность.

## 8. Безопасность и приватность

* Текст сообщений уходит внешнему провайдеру — это должно быть подтверждено явно;
  переменная `KBC_LLM_SEND_CONTENT=true` (по умолчанию `false`).
* В промпт не попадают токены, ключи, пути S3, URL с секретами.
* Логи: без полного текста сообщений, только `message_id`, токены и статус.
* Ответ модели не считается цитатой автора: раздел «Краткое содержание» отделён.
* Ограничение размера входа (по умолчанию 8000 символов) — защита от «промпт-инъекций»
  и неконтролируемого расхода.

## 9. Стоимость и качество

Оценка на 839 сообщений (порядок величины, не биллинг):

| Параметр | Значение |
|---|---|
| вход | 600–900 токенов/сообщение → **0,5–0,8 млн** |
| выход | 150–250 токенов/сообщение → **0,13–0,2 млн** |
| запросов | 839 (кэш делает повторные прогоны бесплатными) |

Фактические числа пишутся в `generations` из поля `usage` ответа API.

Контроль качества (до полного прогона):

1. 30 случайных сообщений: ручная проверка 4 полей (title, summary, category, tags);
2. метрики: доля валидного JSON, доля попаданий в рубрику, доля пустых summary,
   средняя латентность, стоимость;
3. сравнение версий промпта на одном и том же наборе (фиксированные `input_hash`).

## 10. Этапы

| Этап | Содержание | Критерий выхода |
|---|---|---|
| 0 | Provider, схема, кэш, учёт токенов, `generations` + миграция | юнит-тесты с `respx`, 0 реальных вызовов |
| 1 | Промпт v1, `enrich --dry-run --limit 20` | 20 ответов, ручная оценка, 0 невалидного JSON |
| 2 | `enrich --limit 100` с записью в `generations` | измерены токены, стоимость, латентность |
| 3 | `enrich --propose` для всех 839 (в бюджете) | предложения в `Review/`, заметки не изменены |
| 4 | Интеграция в `import_html` (до публикации) | при отказе модели заметка всё равно публикуется |
| 5 | `proposals apply` с `If-Match` и бэкапом | конфликты не перезаписывают правки |

Каждый этап заканчивается отчётом: что сделано, что проверено, сколько токенов потрачено.

## 11. Риски

| Риск | Смягчение |
|---|---|
| Галлюцинации в summary | только по тексту, явная пометка «сгенерировано», ручная проверка |
| Модель придумывает категорию | строгая валидация по списку, иначе `Inbox` |
| Промпт-инъекции в тексте сообщений | текст как данные, без инструментов, лимит входа |
| Неконтролируемый расход | `--budget-tokens`, лимит запросов, кэш |
| Утечка приватного текста | явный флаг отправки, отключение по умолчанию, без логов текста |
| Дрейф качества при смене модели | версии промпта/модели в ключе кэша, сравнение на наборе |
| Медленная работа | 1–2 параллельных запроса, таймауты, retries с backoff |

## 12. Что требуется от вас

1. Подтвердить отправку текста сообщений в DeepSeek (`KBC_LLM_SEND_CONTENT=true`).
2. Дать 3–5 стартовых тем рубрикатора (или разрешить начать с `Inbox` и добавить позже).
3. Задать бюджет на первый прогон (например, 1 млн токенов суммарно).
4. Выбрать режим первого шага: `dry-run` на 20 сообщениях (рекомендую) или сразу 100.
5. Решить, нужен ли `summary` для коротких сообщений (`«хз»`, ссылка без текста) —
   предлагаю: для текста короче 200 символов summary не генерировать.
